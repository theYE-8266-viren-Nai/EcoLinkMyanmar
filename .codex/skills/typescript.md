# TypeScript Skill Guide

## Purpose

This guide explains how TypeScript should be used in EcoLink. TypeScript is the project's safety layer for domain models, UI contracts, Server Actions, validation, and integrations.

## Responsibilities

TypeScript is responsible for:

- Preventing accidental misuse of values.
- Documenting function and component contracts.
- Separating input, database, view, and domain types.
- Supporting safe integration with Zod and Prisma.
- Making refactors predictable.

## Architecture Decisions

EcoLink should use strict TypeScript. Do not weaken compiler settings to avoid fixing types. Runtime validation is still required at trust boundaries; TypeScript only checks code at build time.

## Conventions

Use domain-specific names:

- `RecyclingRequestViewModel`
- `CreatePickupInput`
- `RewardBalanceSummary`
- `OrganizationRole`

Use `unknown` for untrusted values and narrow them with Zod or explicit guards. Avoid `any`.

Derive reusable input types from Zod schemas when the schema is the source of truth.

## Best Practices

Separate types by purpose:

- Input type: what a form or action accepts.
- Domain type: a business concept.
- Database type: generated by Prisma.
- View model: what UI needs to render.
- Integration type: boundary with Clerk, Supabase, Resend, or PostHog.

Keep exported types stable. If a type is only used inside a file, do not export it.

Use discriminated unions for typed result states such as action outcomes.

## Examples

Preferred result concept:

```text
success result: contains data
failure result: contains field errors or form error
```

This is better than returning loosely shaped objects that every caller interprets differently.

## Things To Avoid

- `any`.
- Type assertions that hide real uncertainty.
- Exporting every local type.
- Reusing Prisma model types directly as form types.
- Treating optional and nullable values as the same thing.
- Letting integration response shapes leak throughout feature code.
